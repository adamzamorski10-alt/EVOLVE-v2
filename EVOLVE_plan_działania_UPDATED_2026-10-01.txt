====================================================================== 1.
WIZJA
======================================================================

EVOLVE ma być prywatnym, długoterminowym Personal Performance Coach, a
docelowo Personal Performance OS.

EVOLVE nie jest przede wszystkim: - chatbotem, - generatorem
treningów, - licznikiem kalorii, - aplikacją z wykresami, - kolekcją
ręcznych formularzy.

EVOLVE ma: - rozumieć użytkownika, - zbierać dane, - pamiętać
historię, - rozumieć cele i ograniczenia, - tworzyć plany, - pomagać
wykonywać plan, - rejestrować rzeczywiste wykonanie, - analizować
Expected vs Actual, - wykrywać wzorce, - proponować bezpieczne zmiany, -
wyjaśniać ważne decyzje, - uczyć się indywidualnej reakcji
użytkownika, - z czasem wykorzystywać AI jako warstwę pomocniczą.

Docelowa pętla:

PROFILE + GOALS + CONSTRAINTS + HISTORY + CURRENT STATE ↓ DOMAIN ENGINES
↓ DECISION CONTEXT ↓ DECISION ENGINE ↓ SAFETY ENGINE ↓ PLAN /
RECOMMENDATION ↓ TODAY ↓ EXECUTE ↓ LOG ↓ ANALYZE ↓ EXPECTED VS ACTUAL ↓
LEARN RESPONSE ↓ ADAPTATION PROPOSAL ↓ NEW PLAN ↺

Najważniejsza zasada:

LLM ≠ MÓZG APLIKACJI.

Źródłem prawdy są: - dane, - historia, - deterministyczne obliczenia, -
reguły domenowe, - Decision Engine, - Safety Engine.

AI może pomagać w: - komunikacji, - interpretacji, - naturalnym
języku, - podsumowaniach, - orkiestracji, - interfejsie konwersacyjnym.

AI nie może być źródłem prawdy dla: - historii, - bezpieczeństwa, -
deterministycznych obliczeń, - kalorii/makro, - autorytatywnych
wyników, - stanu użytkownika.

EVOLVE musi być użyteczny bez AI.

8. BEZPIECZEŃSTWO — STANDARD
======================================================================

Bezpieczeństwo ma priorytet nad wygodą implementacji.

Obowiązuje:

AUTHENTICATED PRINCIPAL → CANONICAL USER → OWNED RESOURCE → ACTION

Nigdy:

CLIENT USER_ID → RESOURCE

Nigdy nie ufamy: - user_id z body, - identity_id z body, - profile
ownership z body, - account ID dostarczonemu przez klienta.

Każdy endpoint użytkownika musi mieć: - authentication, - ownership, -
właściwą autoryzację, - walidację, - bezpieczne błędy.

Każdy istotny security fix musi być: - przetestowany, - najlepiej
testowany na dwóch kontach, - zweryfikowany również bezpośrednim API
requestem.

16. ADAPTATION
======================================================================

RPE z Training Coach może być sygnałem.

Nie jest automatycznie źródłem prawdy.

Jedna obserwacja nie powinna prowadzić do dużych zmian bez
wystarczającego evidence.

======================================================================
17. DECISION ENGINE
======================================================================

Hierarchia:

SAFETY → HEALTH / WELLNESS → USER CONSTRAINTS → GOALS → OPTIMIZATION →
PREFERENCES

Decision outcomes:

ALLOW MODIFY ASK BLOCK

Autonomy:

GREEN → safe automatic action

YELLOW → suggestion

ORANGE → confirmation

RED → block

Confidence: - high - medium - low

Confidence nie jest gwarancją prawdy.

Ważne decyzje powinny mieć: - decision - factors - source - confidence -
engine version - context version - outcome - user response.

======================================================================
18. SAFETY
======================================================================

EVOLVE jest systemem wellness / fitness / performance.

Nie jest systemem diagnostycznym ani leczniczym.

Nie powinien: - diagnozować, - przepisywać leczenia, - udawać lekarza, -
przedstawiać niepewnych twierdzeń medycznych jako faktów.

Safety musi być niezależne od: - UI, - planner, - AI.

Minors wymagają age-aware safety i ostrożniejszego traktowania
health/nutrition/performance.

49. PATTERN DISCOVERY
======================================================================

Pattern może być uznany za wartościowy tylko gdy ma: - dane, - okres, -
kontekst, - confidence, - możliwość zakwestionowania, - możliwość
wygaśnięcia.

Nie: “zrobiłeś X raz, więc X powoduje Y.”

Tak: “w obserwowanym okresie X i Y występowały razem w N przypadkach,
ale dane nie potwierdzają przyczynowości.”

======================================================================
50. PERSONAL PERFORMANCE TWIN
======================================================================

Docelowy model użytkownika może opisywać reakcję na: - training load, -
recovery, - sleep, - nutrition, - basketball, - schedule.

Nie jest: - diagnozą, - gwarancją wyniku, - magicznym modelem
przyszłości.

Jest modelem zachowania opartym na danych.

======================================================================
51. PERSONAL EXPERIMENTS LAB
======================================================================

Docelowo:

HYPOTHESIS → CONTROLLED CHANGE → OBSERVATION → ANALYSIS → RESULT →
CONCLUSION.

i nie da się sensownie wyciągnąć wniosku.

======================================================================
52. WHAT CHANGED?
======================================================================

Docelowo system może podsumować:

-   co zmieniło się od poprzedniego okresu,
-   co się poprawiło,
-   co się pogorszyło,
-   które cele są bliżej,
-   jakie decyzje miały wpływ.

Każdy wniosek musi mieć podstawę w danych.

======================================================================
53. WHAT IF?
======================================================================

“Co jeśli będę trenował 4 razy zamiast 3?”

System powinien pokazać: - założenia, - przewidywane konsekwencje, -
kompromisy, - confidence, - ograniczenia.

Nie wolno przedstawiać symulacji jako pewnej przyszłości.

58. FINAL STRATEGIC PRINCIPLE
======================================================================

The goal is not to build the largest possible fitness application.

The goal is to build a system that becomes increasingly useful because
it understands the user’s real context and learns from real execution.

The desired experience is:

“I tell EVOLVE who I am, what I want to achieve, when and where I can
train, what equipment I have and what sport I play.

EVOLVE builds a realistic plan.

Today tells me what to do and why.

I execute.

EVOLVE records what actually happened.

It compares the result with the plan.

It learns how I respond.

It safely proposes what should change.

The next plan becomes better.”

Everything else is secondary.
